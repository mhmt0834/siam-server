# Phase 6.4.3 最终生产加固报告

日期：2026-08-10
候选版本：`restaurant-saas-v1.7-rc1`

## 修改内容

- 依据 50 商家、5 万订单的真实 `EXPLAIN ANALYZE` 增加两项幂等索引，不改字段和订单逻辑。
- Nginx 由单一公网 IP 限流改为“登录令牌身份键 + API 分类 + IP 辅助熔断”，移除 WebSocket 的按 IP 连接上限，并阻断伪造 `X-Forwarded-For`。
- 为 2C2G 增加内存、Swap、负载、容器内存和磁盘阈值；MongoDB 8 的 PID 上限由 256 调整为 384，修复健康检查无法启动 `mongosh` 的问题。
- 增加索引、全业务、网关/API、数据库并发验收脚本；所有数据测试均在隔离临时库或事务回滚环境运行。

## 索引变化

| 表 | 新索引 | 用途 |
| --- | --- | --- |
| `tb_order` | `idx_order_shop_status_completion(shop_id,status,order_completion_time)` | 营业额、趋势、已完成订单、热销商品范围过滤 |
| `tb_order_detail` | `idx_order_detail_order_id(order_id)` | 订单明细及热销商品关联 |

迁移脚本连续执行两次均成功；生产库索引存在且业务数据保持不变。

## SQL 执行计划前后对比

测试集：50 家商家、50,000 个订单、50,000 条订单明细。

| 查询 | 优化前 | 优化后 |
| --- | --- | --- |
| 按订单查明细 | 全表扫描 50,000 行，17.3ms | `idx_order_detail_order_id`，0.0175ms |
| 7 天营业额 | 旧 `create_time` 索引，检查 333 行，1.00ms | 完成时间索引范围扫描，0.54ms |
| 7 天趋势 | 旧索引，1.10ms | 完成时间索引范围扫描，0.543ms |
| 热销商品 | 扫描 50,000 明细并做 50,000 次主键关联，175ms | 完成订单覆盖范围 + 明细索引关联，2.76ms |

五轮各写入 2,000 个订单及明细的中位耗时由 143.036ms 变为 159.089ms（+11.2%），未出现锁等待、错误或明显吞吐退化。

## 限流策略

- 公共 API：IP 辅助熔断 120r/s，burst 240；不以 IP 作为业务身份。
- 登录：IP 6/min，burst 6。
- 提交订单：登录令牌 6/min，burst 3。
- 创建支付：登录令牌 10/min，burst 5。
- 老板接单/完成等写操作：登录令牌 30/min，burst 10。
- memberId、merchantId、shopId 仍由后端从 Token/会话解析并校验，前端字段不参与授权或限流身份判断。
- WebSocket 不设置共享 IP 连接上限，后端继续按 Token 绑定 merchant/shop；断线保留轮询兜底。
- 当前 Nginx 直接面向公网，以 TCP 对端 `$remote_addr` 为真实 IP，覆盖客户端传入的 XFF；未来使用可信 CDN/SLB 时必须逐一配置可信代理 CIDR，禁止信任任意 XFF。

网关验收：伪造 XFF 无法绕过登录限流；同 Token 下单出现预期 429，不同 Token 12/12 正常；共享 NAT 公共扫码 200/200 正常；40 路 WebSocket 握手无 429。

## 2G 资源阈值

当前限制：JVM 容器 768MB（Xmx 512MB）、MySQL 512MB（buffer pool 256MB、最大连接 60）、MongoDB 384MB（WiredTiger 0.25GB、PID 384）、Redis 160MB（maxmemory 128MB、noeviction）、Nginx 96MB。

| 指标 | 告警 | 严重/升级判断 |
| --- | --- | --- |
| 主机可用内存 | <400MB | <250MB；或 <400MB 持续 15 分钟 |
| Swap | >=25% | >=50%；或持续增长并发生换页抖动 |
| CPU/load15 | CPU >=85% 或 load15 >=1.4 | load15 >=1.8；持续 15 分钟升级 2C4G |
| API | P95 >800ms | P99 >2s 或 5xx >1%，持续 15 分钟 |
| MySQL | 连接 >45/60 | 非压测慢查询 >5 条/分钟或连接池持续 >80% |
| 容器内存 | >=80% | >=90% |
| 磁盘 | >=75% | >=85% |
| JVM | 堆使用 >Xmx 80% | 频繁 Full GC/OOM 风险 |

容量预警建议：1–10 家同时活跃、每日不超过约 5,000 单可继续使用 2C2G；超过该范围或任一持续阈值触发时升级 2C4G。50 家以上同时活跃、日订单超过 30,000 或峰值超过 20 单/秒，经 profiling 确认后升级 4C8G。该数量是运维预警线，不是性能承诺。

## 压测与恢复结果

- 全业务集成：24 项测试全部通过，覆盖扫码、菜单、购物车隔离、后端重算金额、订单/支付模拟、老板接单/完成、统计和 A/B 商家隔离。
- 50 商家/5 万订单：并发读取约 754 QPS，并发写入约 639 QPS；0 错误。压测产生的慢查询计数为主动饱和测试数据，执行计划单次仅检查 20 行。
- API 稳态负载：健康接口 2,000/2,000 成功，50.1 RPS，P95 430.3ms/P99 682.0ms；无效桌码 1,000/1,000 正常返回，44.6 RPS，P95 766.0ms/P99 973.9ms。
- MySQL 备份恢复 76 张表通过；MongoDB、Redis 隔离恢复通过。
- Docker Compose 重启与 ECS 实际重启后五个容器均自动恢复并保持 healthy，定时健康检查和备份服务均为 active。
- 重启后资源：磁盘 43%、可用内存约 580MB、Swap 4%、load15 0.73；容器均低于 80% 告警线。

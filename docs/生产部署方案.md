# Phase 6.1 生产部署方案

## 1. 服务器规划

以下为首期经验配置，正式容量必须用真实峰值订单做压测后调整。

| 规模 | 计算资源 | 数据盘 | 公网带宽 | 部署建议 |
| --- | --- | --- | --- | --- |
| 1-10 家测试商家 | 2 vCPU / 4 GB | 80 GB SSD | 5 Mbps | 单机 Docker Compose；JVM 512 MB-1 GB |
| 50-100 家商家 | 8 vCPU / 16 GB | 300 GB NVMe SSD | 20 Mbps | 应用与数据库至少分为两台；数据库使用独立云盘和自动快照 |
| 1000 家以上 | 3 台以上 8 vCPU / 16 GB 应用节点 | 托管 MySQL 高可用、Redis 主从/集群、Mongo 副本集 | 50 Mbps 起并接入负载均衡/CDN | 禁止继续单机；按 API、数据库和异步任务分别扩容 |

Linux 建议 Ubuntu 24.04 LTS 或同级长期支持发行版，使用 x86_64、Docker Engine、Compose v2。系统盘与数据库盘分离；生产数据盘启用云盘快照。公网只开放 80/443，SSH 仅允许固定管理 IP，3306/6379/27017/9200 不开放公网。

## 2. 目录和配置

```text
/opt/restaurant-saas/
├── source/                         # 当前 Git 版本
├── deploy/.env.production          # 仅服务器保存
├── deploy/data/backend/logs/
├── deploy/data/nginx/logs/
└── /var/backups/restaurant-saas/   # 建议独立磁盘或对象存储
```

初始化：

```bash
cd /opt/restaurant-saas/source
cp deploy/.env.production.example deploy/.env.production
chmod 600 deploy/.env.production
mkdir -p deploy/data/{backend/logs,nginx/logs,certbot/conf,certbot/www}
```

在 `.env.production` 中填写强随机密码。`MONGODB_URI` 中密码必须 URL 编码。微信 AppSecret、支付 Key、商户私钥只允许放在服务器密钥环境或云密钥管理服务；当前模板不得保存这些值。

## 3. 构建和 Docker Compose

```bash
mvn -Pprod -pl siam-system/system-provider -am clean package -DskipTests
docker compose --env-file deploy/.env.production \
  -f deploy/docker-compose.production.yml config
docker compose --env-file deploy/.env.production \
  -f deploy/docker-compose.production.yml up -d mysql redis mongodb backend nginx
docker compose --env-file deploy/.env.production \
  -f deploy/docker-compose.production.yml ps
```

Compose 特性：数据库仅在内部网络；MySQL/Redis/Mongo 持久化；Redis 同时启用 AOF 与 RDB；后端/数据库均有健康检查；后端和 Nginx 日志挂载；容器异常自动重启。

每次发布使用不可变镜像标签，例如 `yuking/restaurant-saas:1.6.0-cddc614`，禁止生产长期使用 `latest`。

老板端构建时显式注入 API 地址：

```bash
cd vue-siam-shop
SAAS_API_BASE_URL=https://api.yukingai.cn/siam-server npm run build
```

小程序必须在门店实例中运行 `scripts/apply_restaurant_config.ps1 -ValidateOnly`，取得 DCloud AppID、门店 shopId 等完整资料后再正式注入；不可直接修改模板默认值。

## 4. DNS、Nginx 和 HTTPS

域名审核完成后：

1. 在 DNS 控制台为 `api.yukingai.cn` 添加 A 记录指向服务器公网 IPv4；有稳定 IPv6 才添加 AAAA。
2. 等待 `nslookup api.yukingai.cn` 返回正确 IP，开放安全组 TCP 80/443。
3. 首次启动使用 `NGINX_TEMPLATE=api-http.conf.template`。
4. 申请证书：

```bash
docker compose --env-file deploy/.env.production \
  -f deploy/docker-compose.production.yml --profile tls run --rm certbot \
  certonly --webroot -w /var/www/certbot \
  -d api.yukingai.cn --email YOUR_EMAIL --agree-tos --no-eff-email
```

5. 将 `.env.production` 改为 `NGINX_TEMPLATE=api-https.conf.template`，再执行：

```bash
docker compose --env-file deploy/.env.production \
  -f deploy/docker-compose.production.yml up -d --force-recreate nginx
curl -fsS https://api.yukingai.cn/healthz
```

6. 每日续期检查：

```cron
20 3 * * * cd /opt/restaurant-saas/source && docker compose --env-file deploy/.env.production -f deploy/docker-compose.production.yml --profile tls run --rm certbot renew --webroot -w /var/www/certbot --quiet && docker compose --env-file deploy/.env.production -f deploy/docker-compose.production.yml exec -T nginx nginx -s reload
```

Nginx 同时支持 `/rest/*` 和现有 `/siam-server/rest/*`，WebSocket 路径为 `/rest/merchant/order/realtime`。访问日志不记录查询参数，避免 WebSocket token 泄露；WebSocket 读写超时为 3600 秒。

## 5. 微信小程序生产配置

小程序实例配置：

- API Base URL：`https://api.yukingai.cn/siam-server`
- request/uploadFile/downloadFile 合法域名：`https://api.yukingai.cn`
- socket 合法域名：`wss://api.yukingai.cn`
- 域名必须完成备案、HTTPS 证书链完整且不使用自定义端口。
- AppID 只保存在门店实例和微信后台，不写入可复制模板。

完成域名配置后重新编译，在真机验证登录、扫码、菜单、下单、图片上传/下载、WebSocket 重连和支付回调。商家确认隐私与资质前不得上传提审或启用支付。

## 6. 安全基线

- MySQL 仅创建 `siam_app` 业务用户并限制到业务库；root 仅初始化、备份恢复使用。
- Mongo 使用独立 `readWrite` 业务用户；Redis 使用强密码；三类数据库均不发布宿主机端口。
- 生产 Actuator 只开放 `health,prometheus`，健康详情不返回组件信息；Nginx 只代理 `/healthz`。
- WebSocket 限制到老板端实际 HTTPS Origin，不允许 `*`。
- 单文件最大 10 MB、单请求最大 20 MB；图片上传限制为 JPG/PNG/GIF/BMP/WEBP。
- Nginx 限制连接和 API 请求速率；安全组、系统防火墙与 Docker 网络共同隔离数据库。
- 日志不得包含 token、session_key、手机号、openid、支付 XML、密钥或私钥。日志目录权限建议 `750`，日志文件 `640`。
- 每季度更新基础镜像并在测试环境验证；服务器禁止密码 SSH 登录，使用独立运维账号与密钥。

## 7. 备份和恢复

部署脚本会安装并启用 `restaurant-saas-backup.timer`，每日 02:30 执行，最多随机延迟 15 分钟：

```bash
systemctl status restaurant-saas-backup.timer
systemctl start restaurant-saas-backup.service
journalctl -u restaurant-saas-backup.service
```

备份写入 `/opt/restaurant-saas/backup`，包含 MySQL 一致性逻辑备份、Mongo gzip archive、Redis RDB 和 SHA-256 校验；临时失败目录会自动清理，并通过文件锁防止重复运行。服务器保留 14 天。另一地域对象存储需要单独授权并配置，建议保留 30-90 天、开启版本控制；每月至少在隔离环境做一次恢复演练。

恢复前停止写流量并确认备份校验：

```bash
cd /opt/restaurant-saas/backup/DATE && sha256sum -c SHA256SUMS
CONFIRM_RESTORE=YES \
MYSQL_BACKUP=/opt/restaurant-saas/backup/DATE/mysql-siam_db.sql.gz \
MONGO_BACKUP=/opt/restaurant-saas/backup/DATE/mongodb-siam_db.archive.gz \
/opt/restaurant-saas/docker/scripts/restore.sh
```

Redis 主要保存缓存/会话，优先通过业务数据库重建；确需恢复时停 Redis，将已校验的 `redis-dump.rdb` 放入 Redis 数据卷，再启动并验证会话影响。

## 8. 监控与故障处理

- `restaurant-saas-health.timer` 每 5 分钟检查 Nginx/后端、五个容器健康状态、MySQL/Redis/Mongo ping、可用内存、Swap、15 分钟负载、容器内存和磁盘。磁盘/容器内存达到 75%/80% 告警、85%/90% 失败；可用内存低于 400MB 告警、低于 250MB 失败；Swap 达到 25% 告警、50% 失败；15 分钟负载达到 1.4 告警、1.8 失败。
- ICP/HTTPS 未完成时检查本机 Nginx Host 路由；切换 HTTPS 模板后自动检查正式 HTTPS 域名。
- 使用 `systemctl status restaurant-saas-health.timer` 和 `journalctl -u restaurant-saas-health.service` 查看结果。
- 业务监控：待支付积压、支付回调失败、待接单积压、WebSocket 在线数、订单状态异常。
- 50 家以上建议 Prometheus + Alertmanager + Grafana；外部可用性监控必须部署在另一台机器。

2C2G 升级判断以持续指标为准：连续 15 分钟或连续三次 5 分钟检查出现可用内存低于 400MB、Swap 达到 25% 且仍增长、CPU 超过 85%/load15 达到 1.4、JVM 堆超过 Xmx 80% 或频繁 Full GC、数据库连接超过 45/60、非压测慢查询超过 5 条/分钟、API P95 超过 800ms/P99 超过 2s 或 5xx 超过 1%，应升级至 2C4G；50 家以上同时活跃、日订单超过 3 万或订单峰值超过 20 笔/秒，经分析确认资源瓶颈后升级至 4C8G。商家数/订单量仅作容量预警，不能替代实测指标。

网关限流以登录令牌作为已认证用户/老板的稳定身份键，后端仍从 Token 解析 member/merchant/shop 权限，绝不信任前端传入的 shopId。公网 IP 只作为 120r/s 的辅助熔断维度；登录、下单、支付创建、老板订单写操作分别使用 6/min、6/min、10/min、30/min 的独立令牌桶。WebSocket 不施加按 IP 连接上限，避免同店共享 NAT 误伤。当前 Nginx 是公网边缘，覆盖写入 `X-Forwarded-For: $remote_addr`；只有在前置代理 CIDR 全部明确加入 `set_real_ip_from` 后才允许启用 `real_ip_header`。

故障顺序：先停止发布和破坏性操作，保存日志与时间点；检查 `docker compose ps` 和 `healthz`；数据库异常先确认磁盘/连接数/慢查询；支付异常不得手工伪造成功状态，应核对微信交易单和回调验签；WebSocket 异常确认 Nginx Upgrade 头并依靠轮询兜底。

## 9. 上线回滚

发布前必须完成数据库备份并记录当前镜像标签。应用回滚：

```bash
# 将 BACKEND_IMAGE 改为上一稳定镜像后
docker compose --env-file deploy/.env.production \
  -f deploy/docker-compose.production.yml up -d --no-deps backend
curl -fsS https://api.yukingai.cn/healthz
```

Git 可回到上一稳定标签后重建镜像。数据库只在确认迁移不向后兼容或数据损坏时恢复；先保存故障现场备份，再执行恢复脚本。证书、域名和 `.env.production` 不跟随代码回滚覆盖。

建议首期目标：RPO 不超过 24 小时，RTO 不超过 2 小时；进入真实付费运营后升级为 MySQL binlog/PITR 和更短 RPO。
